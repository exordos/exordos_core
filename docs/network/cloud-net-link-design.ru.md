# Общий CloudNetworkLink

Контракт API и эксплуатационные ограничения:
[OpenStack multicloud](openstack-multicloud.md).

## Назначение

CloudNetworkLink соединяет приватные подсети на разных площадках по L3.
Расположение API Core не определяет топологию соединения. Core хранит желаемое
состояние и управляет шлюзами; пользовательский трафик проходит между шлюзами
площадок напрямую.

Один ресурс содержит два или более подключений подсетей. Фиксированного
верхнего предела числа подключений в общем API нет. Между всеми
подключениями автоматически строится full mesh. Для трёх площадок нужны
три прямых соединения шлюзов; отдельный ресурс на каждую пару не требуется.
Link объединяет подсети с непересекающимися IPv4 CIDR, сохраняя исходные
адреса пакетов. L2 между площадками не растягивается.

## Контракт ресурса

Тело `POST /v1/compute/cloud_network_links/`:

```json
{
  "project_id": "<project UUID>",
  "name": "application-sites",
  "transport": {
    "driver": "openvpn",
    "protocol": "tcp",
    "port": 443
  },
  "endpoints": [
    {
      "subnet": "<Core subnet UUID for cloud A>",
      "gateway_image": "<cloud A image reference>",
      "external_network": "<cloud A external network reference>"
    },
    {
      "subnet": "<Core subnet UUID for cloud B>",
      "gateway_image": "<cloud B image reference>",
      "external_network": "<cloud B external network reference>"
    }
  ],
  "mtu": 1380
}
```

Endpoint ссылается на существующую Subnet каталога Core. Её Network и драйвер
определяют площадку и CloudConnection. В API нет особой стороны `local`,
адреса API Core, `local_cidrs` или назначения на внутренний pool-agent Core.
CIDR берётся из Subnet, адреса шлюзов — из наблюдаемого состояния портов.
Образ и внешняя сеть являются параметрами размещения шлюза на конкретной стороне.

Локальный endpoint задаётся как `subnet`, `agent` и публичный IPv4 `endpoint`.
Нужен готовый маршрутизирующий шлюз с SDK capability `cloud_net_link`; один
физический хост обслуживает один endpoint. Его включение в EVPN и маршруты
к локальным ВМ обеспечивает оператор. Локальный SDN-шлюз создаётся как обычная управляемая Node с приватным
портом и внешним flat-портом; Config/Service запускают отдельный агент link.

## Ответственность механизма

1. Проверить права на все подсети, уникальность подключений и отсутствие
   пересечений CIDR. Подсеть принадлежит одному link,
   чтобы разные ресурсы не управляли её маршрутами одновременно.
2. На каждой площадке обеспечить шлюз, порт в приватной подсети и достижимый
   транспортный endpoint. Облачный драйвер отвечает за создание и удаление
   ресурсов своего провайдера и за правила anti-spoofing.
3. Сформировать для каждого шлюза список всех остальных шлюзов и маршрутов
   к их подсетям. Добавление площадки обновляет конфигурацию всех участников.
4. Применить конфигурацию общим драйвером агента на каждом шлюзе, включая
   forwarding, firewall, маршруты и постоянную конфигурацию транспорта.
5. Через драйвер площадки обеспечить маршрут от локальных ВМ к удалённым
   подсетям через свой шлюз и обратный путь. Для Neutron текущая основа —
   `host_routes` DHCP; уже работающим ВМ потребуется обновление аренды.
6. При удалении облачного подключения сразу отключить его Nova gateway,
   отозвать маршруты и peer-конфигурацию у остальных участников, затем
   удалить оставшиеся принадлежащие механизму ресурсы.
   Незавершённая очистка остаётся в состоянии удаления и повторяется.

Каждый gateway обслуживает все peer-соединения своего link. Full mesh
не требует отдельной шлюзовой ВМ на каждую пару площадок. Драйвер площадки
и драйвер транспорта разделены: провайдер создаёт сетевое подключение,
общий механизм согласует соединения и маршруты.

## Транспорт OpenVPN

Используется OpenVPN с TUN и TLS-аутентификацией
сертификатами. Базовый профиль — TCP/443 с `tls-crypt-v2`; UDP можно выбирать
явно для площадок, где он доступен. Переключение профиля не меняет состав
подключённых подсетей. Автоматическое определение блокировок и переключение
транспорта не поддерживается.

На каждом шлюзе достаточно одного server listener и клиентских экземпляров
к части остальных шлюзов. Роли пары определяются стабильным порядком UUID
подключений: участник с большим UUID инициирует соединение к меньшему.
Так каждая пара получает ровно одно прямое соединение, а всем входящим
соединениям площадки достаточно одного TCP-порта 443. Server listener
обслуживает несколько клиентов. Один шлюз может одновременно принимать
соединения одних площадок и инициировать соединения к другим.

Core автоматически формирует PKI link, сертификаты шлюзов, индивидуальные
`tls-crypt-v2` ключи клиентов и конфигурации OpenVPN. Сертификат сервера
проверяется по роли и идентичности; сервер принимает только явно разрешённые
сертификаты участников. CA private key остаётся в управляющем контуре,
на шлюзы доставляются только необходимые им ключи и сертификаты.

Общий генератор создаёт системные маршруты и серверные CCD `iroute` для
подсетей за клиентскими шлюзами. В shared TUN сервера `iroute` определяет
клиента, которому принадлежит конкретная удалённая подсеть. Клиентские
экземпляры маршрутизируют только подсети своего непосредственного соседа.
Между остальными площадками используется их собственное прямое соединение.
Межплощадочный транзит через третью площадку не включается. Входящий трафик
из TUN к службам самого шлюза блокируется отдельно от forwarding;
ответы ESTABLISHED,RELATED на исходящие запросы шлюза разрешены.

При заранее известных подсетях full mesh не требует BGP. Существующий EVPN
остаётся локальным механизмом SDN; интеграция его маршрутов со шлюзом
не диктует транспорт между облаками.

TCP/443 не делает OpenVPN обычным HTTPS и не гарантирует прохождение DPI.
`tls-crypt-v2` защищает управляющий канал, но доступность транспорта требуется
проверять на целевых площадках. TCP-транспорт может ухудшать задержку и
пропускную способность при потерях и перегрузках; его выбор здесь обусловлен
ограничениями доступности UDP.

Основание: [OpenVPN: transport options](https://github.com/OpenVPN/openvpn/blob/release/2.6/doc/man-sections/link-options.rst),
[TLS options](https://github.com/OpenVPN/openvpn/blob/release/2.6/doc/man-sections/tls-options.rst),
[server routes and CCD](https://github.com/OpenVPN/openvpn/blob/release/2.6/doc/man-sections/server-options.rst).

## API Core и локальная сеть Core

Core сначала создаёт порты и резервирует внешние адреса всех шлюзов через
API провайдеров. После этого известны адреса всех участников и можно
сформировать полные bootstrap-конфигурации соединений.

Начальная конфигурация доставляется через API провайдера: для OpenStack —
Nova `user_data` / cloud-init. Драйвер OpenStack проверяет фактический размер
bootstrap после gzip и base64 перед созданием ВМ: предел Nova — 65 535 символов.
При превышении возвращается ошибка с размером payload и лимитом провайдера.
Cloud-init устанавливает OpenVPN и необходимые
зависимости из доступных репозиториев, затем конфигурацию транспорта, forwarding,
маршруты и автозапуск без обращения к API Core из гостя.

Агентам шлюзов нужен доступ к управляющим API Core для последующих изменений.
Их адреса задаются отдельно от CloudNetworkLink. Агент повторяет подключение,
пока путь управления не станет доступен; поднятие самого link от него
не зависит. Сеть приватного API может быть ещё одним участником link.

После применения конфигурация и маршруты сохраняются на шлюзах.
Потеря API Core не останавливает существующие соединения; изменения
состава и восстановление ресурсов требуют возвращения управления.

Если API Core должен обслуживаться только из приватной сети, его локально
подключают к подсети, участвующей в link, и обеспечивают обратный маршрут.
Это задача локального размещения API и маршрутизации. Она не добавляет Core
в путь пакетов между другими площадками и не меняет контракт link.

## Проверки и ограничения

- Две облачные подсети соединяются без VPN-интерфейсов на хосте Core.
- Первоначальное соединение поднимается при недоступном из гостя API Core.
- TCP-профиль работает при запрещённом межплощадочном UDP.
- Третья площадка получает прямую связь с каждой из первых двух.
- Добавление и удаление участника согласует peers, маршруты и очистку.
- Потеря площадки с API Core сохраняет связь между двумя другими площадками.
- Недоступный peer отражается в состоянии link; запуск ВМ сам по себе
  не считается подтверждением готовности соединения.
- Изолированные проекты и неподключённые сети не получают доступа.
- Проверка отказа площадки выполняется на независимых площадках: два проекта
  одной OpenStack-инсталляции подтверждают только логическую связность.

Проверки независимых отказов провайдеров требуют независимых инсталляций:
проекты одной инсталляции имеют общую область отказа.
Selectel и VK Cloud/Sprut отдельно не проверены. Пропускная способность и
поведение DPI на целевых провайдерах не измерялись.

На Core и шлюзах требуется SDK с `gcl_sdk.cloud.openvpn` и
`OpenVPNCapabilityDriver`. Образы PaaS должны содержать агентов, использующих
настроенный идентификатор Node в Core. См. [требования к SDK и агентам](openstack-multicloud.md#sdk-and-agent-requirements).

Сертификаты автоматически продлеваются за 30 дней до истечения. CA при
продлении сохраняет ключ, чтобы старые и новые сертификаты могли сосуществовать
при поэтапном применении. На хосте gservice требуется OpenVPN 2.6+ для генерации
`tls-crypt-v2` ключей; VPN-интерфейсы на нём не нужны.

Явное восстановление облачного шлюза: `POST .../cloud_network_links/<UUID>/actions/
recover_gateway/invoke` с телом `{"subnet": "<UUID>"}`. Оно требует права update,
заменяет Nova server через API провайдера и сохраняет порт и floating IP.
Доступ к агенту сломанного шлюза не требуется. Потерянная ВМ восстанавливается
автоматически. Готовность проверяется для текущего server ID и target hash.

Отзыв конфигурации недоступного локального endpoint остаётся асинхронным;
оператор отвечает за доступность и физическое отключение своего шлюза.

Ограничения: IPv4, один шлюз на endpoint, без HA/BGP,
без автоматического выбора транспорта, с обновлением DHCP у работающих ВМ
после изменения состава. `ACTIVE` подтверждает состояние туннелей;
проверка приложений и правил security groups выполняется отдельно.
