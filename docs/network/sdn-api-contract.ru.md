# Сетевые ресурсы SDN

[Сущности и схемы dataplane](dataplane.ru.md).

Новый контракт требует совместимых версий Core и SDK.
Если `Node.networking` отсутствует, сохраняется прежнее поведение плоской сети.

## Связи и владение

| Ресурс | Связь | Вычисляемые поля, только чтение |
| --- | --- | --- |
| Node | `networking` только при создании | `ports` |
| Port | nullable `node`, автоматический или явный `index` | сеть, фактические IP/MAC, списки SG/IG |
| Address | неизменяемый `kind`, nullable `port` для floating | состояние выделения и публикации |
| PortSecurityGroup | неизменяемая пара `port`, `security_group` | — |
| PortIdentityGroup | неизменяемая пара `port`, `identity_group` | — |
| SecurityGroupRule | SG, направление, протокол, опциональные порт и remote | — |
| SecurityGroup | имя, описание | `rules` |
| IdentityGroup | сеть при создании | бит идентичности |

Обратные списки портов у Subnet, SG и IG не добавляются.
Связи many-to-many и правила SG — самостоятельные ресурсы: другой манифест
может добавлять собственные связи, не переписывая чужие списки.

Переключатели DHCP, DNS и автоматической identity находятся только в полях
`Port.dhcp`, `Port.dns`, `Port.network_identity`. Членство в группах задаётся
только ресурсами PortSecurityGroup и PortIdentityGroup. В `Port.config` и
`interfaces[].config` остаётся только запрос `public` вида `simple`;
списки групп и переключатели внутри `config` отклоняются. Старые манифесты
нужно перевести на привязки или `networking`. Миграция переносит сохранённые
настройки портов и преобразует шаблоны групп NodeSet в `networking`.
Для Node с ещё не созданными привязками групп нужно завершить подготовку
или преобразовать декларацию перед обновлением.

Привязанные к порту адреса запрашиваются через коллекцию Address с фильтром
`port`. Результат создания Node содержит `ports`; связи и адреса этих портов
доступны через собственные коллекции. Фактический MTU находится в
`Network.driver_state.mtu`. Поля представления используют существующий
механизм custom props Restalchemy.

При создании Port и Address задаётся ровно одно поле: `subnet` или `network`.
Выбор сети требует единственной подходящей доступной подсети; неоднозначность
возвращает 409 со списком UUID кандидатов. `floating_pool=true` отдельно
обозначает внешний пул; RFC1918 допустим. Пул обязан быть address-only
(`placeable=false`); изменение признака требует операторского права
`network.subnet.floating_pool`, не выдаваемого владельцу проекта автоматически. `shared_pool` и публичный доступ
к Network определяют доступность выделения. Явный IP в чужом пуле требует
`network.address.explicit_address`. FIP и его Port принадлежат одному проекту.

Address требует `kind`: `reservation` резервирует IP без порта, `floating`
может привязываться к Port. Поддерживается один FIP на порт. Смена kind,
подсети или уже выделенного адреса запрещена. Использование reservation
как приватного IP порта в этом контракте не определено.

## Создание ноды и изменение подключений

```json
{
  "name": "vm", "cores": 1, "ram": 1024,
  "disk_spec": {"kind": "root_disk", "image": "ubuntu_24.04"},
  "networking": [{
    "port": {"network": "PRIVATE_NETWORK_UUID"},
    "security_groups": ["SG_UUID"],
    "floating_ip": {"network": "EXTERNAL_NETWORK_UUID"}
  }]
}
```

`port` и `floating_ip` также принимают UUID ранее созданных свободных ресурсов.
Node, новые Ports, связи и FIP создаются одной транзакцией. `networking=[]`
отключает автоматическое создание портов. Null и смешивание с прежними
interfaces запрещены. После создания используются API самих ресурсов.

У отключённого порта `node=null`, `index=null`. При подключении пропущенный
индекс атомарно получает минимальное свободное число от нуля. Явный null
при подключении запрещён; изменение индекса подключённого порта также.
Отключение не перенумеровывает оставшиеся порты. Индекс 0 — основной
интерфейс загрузки и установки образа.

Несколько NIC и подключение/отключение работающей ВМ поддерживаются в live
и persistent конфигурации libvirt. Потеря последнего NIC не уничтожает ВМ.
Первичная установка образа требует основного NIC.

Удаление SDN-ноды отключает и сохраняет её порты, включая сгенерированные.
Чужие зависимости не удаляются каскадом: возвращается 409. Перенос Port/FIP
требует явного отключения/отвязки, затем нового подключения/привязки.
IP/MAC и опубликованный FIP удерживаются до подтверждения удаления
назначенным гипервизором. Недоступность хоста не освобождает адреса.

Каждый запрос создания Node без UUID создаёт новый ресурс. Клиент может
задать UUID ресурса для идентификации своего запроса создания.

NodeSet применяет networking как шаблон новых реплик. Допустимы только
объекты создания с автоматическими IP/MAC/FIP. Обновление шаблона сохраняет
существующие реплики и их связи; фиксированные адреса и UUID в шаблоне запрещены.

## Фильтрация и идентичность

Нет SG-связей — ingress и egress разрешены. При наличии связей разрешения
SG объединяются, остальное запрещено. Назначенная пустая SG запрещает всё.
Удаление последней связи возвращает разрешение всего трафика на уровне SG.
Anti-spoofing независим от SG и включён по умолчанию.

Неявной default SG нет. Защищённая автоматическая IG с детерминированным UUID
объединяет порты всей Network, в том числе разных подсетей.
`network_identity=false` исключает порт из неё.

`remote_group` в правиле обозначает IG, допустим только для ingress
и исключает `remote_ip`. Протоколы: any, tcp, udp, icmp. Единственный
номер порта 1–65535 допустим только для TCP/UDP; диапазонов пока нет.

Объявленные при установке связи SG и правила блокируют первоначальную
активацию порта до создания ресурсов, включая загруженные зависимые Elements.
Последующие изменения политики согласуются независимо.

## Частичные декларации и состояние

Пропуск поля сохраняет значение. Словари с известной схемой объединяются
рекурсивно: `Network.driver_spec`, `NetworkFunction.config`; `{}` ничего
не меняет. Списки заменяются целиком, `[]` задаёт пустой список. Null
очищает или включает наследование только там, где это разрешает схема.
Defaults и вычисленные значения не дописываются в декларации.
Вычисляемые поля не принимаются как SQL-фильтры и сортировки: 400.

Настройки отделены от результата: Network driver_spec от driver_state/MTU,
Subnet DNS/routes от effective-полей, NF config от generated/effective config.
MTU null наследует underlay минус накладные расходы VXLAN без смены VNI/RT.

DNS и proxy перехватывают запросы к metadata IP и фактическому шлюзу подсети.
Запросы к другой ноде на портах DNS, Orch/Status и boot API проходят через обычную
сеть и её правила безопасности, включая control plane вложенного реалма.
Адреса перехвата входят в NF descriptors порта: их изменение меняет target hash
и вызывает повторное применение flows. DHCP discovery остаётся исключением.

Статусы FIP: UNBOUND, IN_PROGRESS, ACTIVE, ERROR, DELETING. ACTIVE и освобождение
требуют сообщения назначенного агента с текущим hash и временем после
публикации target. Удаление может ожидать доступности хоста.

## Манифесты и поставка

[Полный пример](../../exordos/manifests/examples/sdn-networking.yaml) содержит
Node, Port, автоматически выделяемый FIP, SG, правило и связь. Перед применением
выберите пул, образ и разрешённый CIDR. Требуются подготовленные SDN-гипервизоры
и внешняя связность; создание пула само по себе не настраивает гипервизоры.

Второй манифест импортирует Port и создаёт свои FIP/связи. Повторное применение
базового манифеста сохраняет независимые связи и автоматический индекс.
EM работает с полномочиями оператора: явный project_id — декларация оператора,
пропуск использует проект EM-агента. Право foreign_subnet относится только
к прежним interfaces, а не к приватным связям нового API между проектами.

Inline-создание проверяет права соответствующих ресурсов: Port create/update,
Address create/update и создание SG/IG-связей. Явный IP в чужом пуле требует
того же отдельного права. Владельцы проекта получают CRUD новых правил и связей;
права публикации общих пулов и фиксации чужих адресов остаются отдельными.

Core и SDK нужно поставлять согласованным набором. Одних числовых bounds
недостаточно: сначала выпуск SDK, затем Core и обновление dependency locks.
Перед обновлением работающего SDN требуется новый SDK-агент
на всех гипервизорах. Плоские сети сохраняют прежнее представление одного NIC;
миграция не изменяет их driver_spec.

До обновления Core агенты должны поддерживать NF destination selectors.
Старый агент принимает это поле, но ставит прежние правила только по порту;
его последующее обновление само по себе не меняет уже подтверждённый hash.

## Сохранённые декларации и обновление

Миграция 0006 переносит сохранённые настройки Port в канонические поля и связи,
а декларации Node/NodeSet — в EM и целевых ресурсах. До обновления завершите
создание ожидающих связей с группами и раскройте ссылки в конфигурациях
интерфейсов и переключателях. Списки групп Node/Port при миграции должны
содержать явные UUID. Исходные манифесты должны использовать
канонический формат. Откат с управляемыми SDN-декларациями требует восстановления
резервной копии БД; непредставимые шаблоны NodeSet останавливают откат.

Если 0006 уже применена, миграция 0009 повторяет нормализацию, включая
фактические снимки Node в UA, добавляет сохранённый activation barrier NodeSet
и удаляет неиспользуемую таблицу creation receipts. До запуска 0009 все
объявленные в манифестах SecurityGroupRule должны существовать в БД; иначе
миграция останавливается до изменения данных. Это исключает активацию
перенесённого шаблона NodeSet до появления его начальных правил. Миграции Core
нужно применить явно перед перезапуском его служб.
