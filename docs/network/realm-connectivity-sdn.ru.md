# SDN связности реалмов (EVPN/VXLAN)

Дизайн-документ по изоляции сетей реалмов и публичной связности в экосистеме
exordos.

> **Это сокращённый пересказ** английского
> [`realm-connectivity-sdn.md`](realm-connectivity-sdn.md) — он источник
> истины, здесь только контекст и решения. Приведённые ниже формулировки
> относятся к моменту утверждения дизайна; что именно собрано, смотрите в
> английском документе, а как этим пользоваться —
> в [`private-network.md`](private-network.md).

## Контекст и цели

Экосистемная инсталляция размещает **реалмы** — вложенные полноценные
инсталляции `exordos_core`, работающие как VM на железе экосистемы. Текущая
сетевая модель — один плоский L2-сегмент (`flat_bridge`, ISC DHCP на
linux-bridge) на всех, что даёт:

- отсутствие изоляции между реалмами (общий broadcast-домен, пересекающиеся
  приватные CIDR на общем железе);
- отсутствие управляемого публичного ин/эгресса для сервисов реалмов.

Публичная связность частично закрыта **Шагом 0**: capability `border_agent`
universal-agent'а на корной ноде даёт egress-SNAT и `(ip, port)`-DNAT
форварды через nftables. Этот документ фиксирует целевую архитектуру
(изоляция + обобщённая связность) и скоуп первого SDN-инкремента.

## Архитектурные решения

Решения ниже зафиксированы полной ревизией дизайна (2026-07-17).

### 1. Data plane: OVS + gobgp, переиспользуем `evpn_connector`

Данные плоскости — проект `evpn_connector` (gobgp по gRPC + Open
vSwitch/VXLAN). Он уже умеет EVPN Type-5, VRF, ECMP, ARP-proxy и
anycast-префиксы с health-check'ами, а конфигурируется простыми per-host
JSON-файлами клиентов — идеально ложится на доставку universal-agent'ом.
FRR + нативный Linux VXLAN (переписывание reconcile-логики) и OVN (тяжёлая
зависимость, чужая модель мира) рассмотрены и отклонены.

### 2. Модель оверлея: L3 EVPN Type-5 (реалм = VRF)

Каждому реалму родительская инсталляция выделяет VRF (VNI + route target).
Каждая VM анонсируется `/32`-маршрутом Type-5 в свой VRF; растянутого L2 и
BUM-трафика нет; ARP отвечается локально на хосте (ARP-proxy в
`evpn_connector`). Реалмы изолированы даже при пересекающихся приватных
CIDR. L2-сегменты (Type-2) — возможная будущая опция, не часть базового
дизайна.

### 3. Boot-сеть остаётся flat на underlay

PXE-boot-сеть (подсеть с `next_server` + `ip_discovery_range`) — это
**инфраструктурная** сеть инсталляции, не тенантская: в ней ходит только
Seed OS-провижининг под контролем инсталляции. Она сознательно остаётся
**вне оверлея**, на плоском underlay. Следствие: гипервизорам нужна
L2-смежность на underlay для PXE.

Отдельный (не SDN) трек: убрать PXE для VM вообще — агент гипервизора пишет
образ напрямую в диск VM; PXE остаётся только для bare-metal. Этот трек
снимает требование L2-underlay, но не блокирует SDN.

### 4. Host-local DHCP для оверлейных сетей

Гостевые сети в оверлее не достучатся broadcast'ом до центрального ISC.
На каждом гипервизоре работает маленький **локальный DHCP-ответчик**,
отвечающий локальным VM из фактов control plane (`Port.mac/ipv4`,
`Subnet.routers/dns_servers`, MTU). Ни relay, ни рантайм-зависимости от
корной ноды при выдаче адресов. Конфиг ответчика доставляется тем же
per-host агентским ресурсом, что и EVPN-конфиги.

### 5. Топология публичной связности — параметр инсталляции

Дизайн обязан работать в **минимальной топологии**: один uplink, без eBGP к
провайдеру (статический некстхоп), как на текущем dev-стенде. Более богатые
топологии (несколько uplink'ов, провайдерский eBGP, anycast) выражаются
размещением **edge-роли** на большем числе нод. «Border» — всегда
роль/capability на нодах, никогда не отдельная коробка; border Шага 0 на
корной ноде — вырожденный случай «edge-роль ровно на одной ноде».

### 6. Egress: распределённый SNAT (DVR) по умолчанию

Каждый гипервизор SNAT'ит трафик своих локальных VM реалма в свой uplink-IP
(per-VRF route-leak в глобальную таблицу): нет SPOF, нет hairpin'а,
горизонтальное масштабирование. Трейдофф: исходящий трафик реалма идёт с
многих IP нод.

**Кодифицировано (2026-07-19)** в агентском драйвере
(`gcl_sdk/.../drivers/evpn.py`): `EvpnPort._apply` вызывает
`_ensure_vni_egress`, когда сабнет CP несёт шлюз (`dhcp.routers[].via`)
— один namespace `snat<vni>` на VNI на хост, нога шлюза в EVPN-бридже со
своим client-конфигом (шлюз `/32` + `0.0.0.0/0`, host-уникальный
неимпортируемый `exp_rt` от hostname), transfer `/30` на VNI из
выделенного диапазона, двойной masquerade. Сносится с последним гостем
VNI на хосте (`_gc_vni_egress`).

Планируется per-realm опция **«stable egress IP»** (после Инкремента 1):
default-маршрут VRF реалма указывает на edge-ноду, которая SNAT'ит в один
стабильный адрес — тот же механизм `SnatRule`, что в Шаге 0, ценой
hairpin'а.

### 7. Ingress: LBaaS-инстансы реалма, целевая доставка — routed anycast VIP

Центральный LB корной ноды обслуживает только коровые сервисы.
Реалмовый/тенантский ingress идёт через **LBaaS-инстансы**. Целевая доставка
трафика до LBaaS-инстанса внутри VRF — **маршрутизируемый публичный VIP без
NAT**: LB-ноды держат VIP на loopback и анонсируют его anycast-маршрутом
Type-5 (`ClientEdgePrefixAnycast`, с health-check); edge-ноды просто
маршрутизируют. Это сохраняет клиентский IP, даёт HA/ECMP без keepalived и —
в отличие от DNAT на edge — совместимо с распределённым egress (DNAT на edge
при DVR-возврате асимметричен и ломает conntrack).

Border-`Forward` (DNAT) Шага 0 остаётся переходным механизмом, пока edge —
одна нода (симметрия гарантирована), и для не-LB `(ip, port)`-форвардов.
Публичные адреса управляются как первоклассный **пул PublicIP** с IPAM с
первого дня (пул размера 1, растущий).

### 8. BGP-фабрика: route-reflector на корной ноде; потеря RR не должна рвать data plane

Все хосты пирятся `l2vpn-evpn` с gobgp **route-reflector'ом** (capability
`bgp_rr`) на корной ноде; full-mesh не используется (конфиг ноды статичен,
добавление ноды никого не трогает).

Требования живучести:

- **LLGR (long-lived graceful restart) с большим retain (напр. 24 ч) на всех
  сессиях с первого дня**: при потере RR маршруты помечаются stale, а не
  отзываются — существующая связность продолжает работать (fail-static),
  приостанавливается только сходимость изменений.
- **Второй RR** — как только в инсталляции появляется вторая подходящая нода.
- Обязательный тест Инкремента 1: убить RR и убедиться, что OVS-флоу
  выживают. `evpn_connector` реконсилирует флоу из RIB локального gobgp
  (`ListPath`), поэтому видимость stale-путей надо подтвердить; если stale
  исчезают из RIB — в `evpn_connector` добавляется явный fail-static-режим.

### 9. Доставка конфигов: universal-agent capabilities, без общего каталога

Используется путь доставки, обкатанный Шагом 0 (без промежуточного
shared-dir-механизма):

- kind **`evpn_node`** на агенте каждого гипервизора: per-host набор
  клиентских JSON `evpn_connector` (mac, `/32`-маршруты, VNI, RT), записи
  локального DHCP и параметры gobgpd-сессии (source IP, адреса RR);
- kind **`bgp_rr`** на агенте корной ноды: конфиг рефлектора (LLGR,
  passive-пиринг).

Новый сетевой драйвер **`ovs_evpn`** (entry point `gcn_network_driver`) —
чистый *вычислитель* этих target-ресурсов из моделей
`Network`/`Subnet`/`Port` (тот же builder-паттерн, что border/LB); сам на
хосты не ходит.

**Проводка гостя шедулится на гипервизор (2026-07-19)**: гость втыкается
в br-int *своего гипервизора*, поэтому `evpn_port`/`evpn_host` уходят
агенту ноды-гипервизора, а не самому гостю. Маппинг —
`MachinePool.hypervisor_node` (ставится `exordos compute hypervisors
register-agent --pool`); драйвер резолвит `port.node → Machine → pool →
hypervisor_node` и откладывает эмиссию, пока machine гостя не размещена
на пуле. Пул без маппинга сохраняет прежнее поведение (нода проводит
себя сама — self-hosted-fabric путь спайка).

**`ofport` — факт со стороны хоста**: интерфейсы VM втыкаются в OVS через
libvirt (`virtualport type='openvswitch'`), агент репортит фактический
ofport, и хостовый драйвер подставляет его в клиентские конфиги. Control
plane управляет только mac/ip/VNI.

### 10. Рекурсивная модель: каждый уровень крутит свой независимый SDN

Реалм — полноценная инсталляция и запускает **свой** SDN поверх VRF-сети,
которую дал родитель (оверлей родителя = underlay ребёнка; VTEP'ы ребёнка —
адреса его нод-VM внутри родительского VRF). VNI/RT-пространства уровней —
непересекающиеся вселенные, **межуровневой координации и передачи аллокаций
не существует**. Каждая кора аллоцирует VNI/RT автоматически из своего
`Ipam` при создании `Network` с драйвером `ovs_evpn`. Единственное, что
родитель даёт реалму, — его VRF-сеть, создаваемую realm-builder'ом
экосистемы.

### 11. MTU — первоклассное поле

Единственный кросс-уровневый контракт рекурсии — бюджет MTU: каждый уровень
вложенности стоит ~50 байт VXLAN-инкапсуляции. `Network`/`Subnet` несут
явный MTU; MTU оверлея = MTU underlay − 50 и выдаётся гостям через
DHCP-опцию `interface-mtu`. Jumbo-фреймы (≥1600, лучше 9000) на физическом
underlay — рекомендация, делающая первые уровни вложенности бесплатными.

### 12. Упаковка: SDN-стек — опциональная часть элемента core

OVS, gobgpd, `evpn_connector` и DHCP-ответчик **не** запекаются в базовый
образ и **не** являются отдельным элементом: они поставляются опциональной
частью **элемента core**, устанавливаются на живые ноды штатным механизмом
элементов, с CLI-командой включения/выключения роли на ноде. Версии SDN тем
самым связаны с релизом core, что также фиксирует совместимость
`ovs_evpn`-драйвера и `evpn_connector`. Вытекающие требования: доступность
артефактов через repo-chain на каждом уровне вложенности; идемпотентная и
обновляемая установка.

### 13. Сосуществование и конечное состояние: со временем всё на OVS

Инкремент 1 держит два драйвера рядом: сети реалмов на `ovs_evpn`
(realm-builder создаёт по сети на реалм), инфраструктурные сети — на
`flat_bridge`. Целевое состояние — единая дата-плоскость на OVS; перевод
инфраструктурных сетей на OVS — фаза дорожной карты (boot-сеть семантически
остаётся flat-on-underlay независимо от технологии бриджа). Существующие
реалмы мигрируются пересозданием; живая миграция flat→EVPN вне скоупа.

## Скоуп Инкремента 1

Два чекпойнта с переоценкой между ними.

### Чекпойнт 1 — спайк дата-плоскости + control-plane клей

Стенд: корная VM плюс одна-две новые гипервизор-VM на хост-машине.

1. Ручной спайк дата-плоскости (без CP): OVS + gobgpd + `evpn_connector` на
   гипервизорах, RR с LLGR на коре. Валидация: VM↔VM внутри VRF, изоляция
   VRF↔VRF, per-node SNAT egress, **LLGR fail-static** (убить RR —
   связность живёт), MTU-бюджет end-to-end.
2. Control plane: драйвер `ovs_evpn`, capabilities `evpn_node`/`bgp_rr`,
   локальный DHCP-ответчик, аллокатор VNI/RT в `Ipam`, поле MTU,
   ofport-факты.
3. Упаковка: SDN-часть в манифесте элемента core + CLI-включение роли.

### Чекпойнт 2 — два изолированных реалма

Realm-builder экосистемы создаёт per-realm `ovs_evpn`-сеть. End-to-end: два
реалма на общем железе, взаимно недостижимы, оба полностью работоспособны
(PXE-загрузка по плоской boot-сети, egress в интернет работает).

## Дорожная карта (после Инкремента 1)

- Anycast VIP для LBaaS-ингресса (заменяет DNS-записи на `ipsv4`).
- Per-realm опция «stable egress IP» через edge-ноду.
- Второй route-reflector.
- Инфраструктурные сети на OVS.
- Прямая запись образов VM (PXE только для bare-metal).
- Выделенные публичные IP из выросшего пула; интеграция с DNS.

## Открытые вопросы

- Поведение `ListPath`-реконсайла `evpn_connector` при LLGR — проверяется в
  чекпойнте 1; если stale-пути выпадают из RIB, `evpn_connector` патчится
  fail-static-режимом.
- DP-артефакты элемента, целящиеся в саму ноду-гипервизор (а не в VM
  элемента) — ожидаемо работает как border Шага 0 на корном агенте;
  подтвердить при упаковке в чекпойнте 1.
- Мульти-гипервизорный флоу инсталляции (добавление compute-нод к коре) —
  предусловие чекпойнта 2; переоценить скоуп после чекпойнта 1.
