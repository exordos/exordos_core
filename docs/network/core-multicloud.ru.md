# Core multicloud

Одна инсталляция Core может использовать другую как облачного провайдера.
Верхний Core управляет желаемым состоянием приложений. Удалённый Core создаёт
ВМ, диски и сети на выделенных нативных гипервизорах. Инсталляции общаются через
обычные API в рамках проекта, без доступа к базам данных друг друга.

## Требования

На оба control plane установите согласованные версии Core и SDK с драйвером
Core. Удалённая инсталляция должна предоставлять нативные гипервизоры `libvirt`
или `exordos_local_hyper` с включённым OVS. Пулы и ресурсы должны принадлежать
проекту, указанному в подключении. Используйте отдельный проект и учётную запись
с правами на compute, сети, порты, security groups и configs. Оператору верхнего
Core нужны права на регистрацию облачного гипервизора.

Образ гостя должен содержать совместимый universal agent по пути
`/usr/bin/exordos-universal-agent`, systemd и cloud-init. Для верхнего Core
создаются отдельные агент, идентификатор, ключ и каталог состояния
`/var/lib/exordos/core-provider/<connection>`. Агент удалённого Core продолжает
управлять базовой ВМ. Гости должны достигать Orch и Status API верхнего Core.

Для удалённого User API через недоверенные сети используйте HTTPS. Для
доверенной управляющей сети допускается HTTP. Файл подключения содержит секреты
и требует защиты. Учётные данные и исполняемое содержимое bootstrap скрыты в
ответах tenant API и при журналировании тел чувствительных запросов.

Bootstrap Config провайдера управляется через свой Node. Прямое изменение
возвращает HTTP 409; отдельное удаление также возвращает 409, пока Node существует.
Удаление Node очищает его bootstrap. Доставка Config может обновлять его статус,
а после удаления Node сборщик может очистить оставшийся bootstrap Config.

## Регистрация провайдера

Создайте JSON-файл с правами `0600`, заменив значения примера:

```json
{
  "kind": "core",
  "api_url": "https://remote-core.example.org",
  "project_id": "11111111-1111-4111-8111-111111111111",
  "hypervisors": ["22222222-2222-4222-8222-222222222222"],
  "auth": {"username": "provider", "password": "REPLACE"}
}
```

Для инсталляций с собственным IAM-клиентом объект `auth` также принимает
`client_uuid`, `client_id` и `client_secret`.

```bash
exordos compute hypervisors add --name remote-core --kind core \
  --driver-spec-file core-provider.json
```

Эквивалентный запрос — `POST /v1/compute/hypervisors/` с этим объектом внутри
`driver_spec`. Подключение предоставляет верхнему scheduler обычный облачный
пул. URL API, проект и список удалённых гипервизоров образуют неизменяемую
область подключения. Для её изменения зарегистрируйте другое подключение.

Создайте [логическую сеть](logical-networks.ru.md) и подсеть, включив UUID нового
верхнего гипервизора в `hypervisors`. Размещённые там Node и NodeSet создают ВМ
через удалённый Core. Детерминированные UUID и метки принадлежности обеспечивают
повторяемость операций и защищают посторонние удалённые ресурсы от очистки.

## Приватная связность

Логическая сеть может объединять нативные подсети, OpenStack и удалённый Core.
Для управляемого шлюза на площадке Core задайте `gateway` в подсети или
`network_defaults` в подключении:

```json
{
  "external_subnet": "33333333-3333-4333-8333-333333333333",
  "gateway_image": "https://images.example.org/exordos.raw.zst",
  "gateway_cores": 1,
  "gateway_ram": 1024,
  "gateway_disk": 8,
  "role": "server"
}
```

`external_subnet` — подготовленная оператором транспортная подсеть удалённого
проекта. Её адреса должны быть доступны другим шлюзам. Провайдер создаёт ВМ с
приватным и транспортным NIC, запускает OpenVPN и устанавливает маршруты через
зарезервированный приватный адрес. Для SDN-транспорта создаётся отдельная VPN
security group; flat-транспорт защищает периметр оператора. Восстановление шлюза
создаёт новую ВМ с сохранением портов и адресов. Security groups рабочих ВМ
передаются через удалённый API.
Они продолжают применяться при `port_security=false`, отключающем защиту от
подмены MAC/IP: эти настройки независимы.

## Жизненный цикл ресурсов

Корневой диск и диски данных создаются вместе с ВМ. Поддерживаются увеличение
CPU, памяти и подключённых дисков. До создания диска удалённой ВМ он остаётся в
ожидании. Для активного состояния необходимы готовность удалённых ресурсов и
сходимость гостевого агента верхнего Core. Ёмкость агрегируется по tier и
постоянству дисков; физический пул выбирает удалённый scheduler, который также
проверяет размещение, свободное место и квоты.

Отдельные неподключённые диски, отключение и перенос дисков, смена дисковой
политики, переустановка образа существующей ВМ и явные операции питания
отклоняются. Для смены образа замените ВМ. Недоступность удалённого API
приостанавливает reconciliation; работающие гости и приватная связность
продолжают обслуживаться data plane. Удаление верхнего workload очищает его
удалённую ВМ, диски и bootstrap. Удаление логической сети ожидает очистки
удалённых сетей и шлюзов.
