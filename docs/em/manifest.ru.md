# Руководство по манифестам

## Введение

**Манифест** — это YAML-файл, декларативно описывающий всё, что нужно элементу для работы на платформе
Exordos Core: инфраструктуру (виртуальные машины, группы узлов), сервисы (systemd-юниты), конфигурационные
файлы, DNS-записи, балансировщики нагрузки, секреты (сертификаты, пароли), IAM-сущности и переменные
платформы.

Манифест — это чертёж; **элемент** — это запущенный экземпляр, созданный из него. Связь аналогична
исходному коду и запущенному процессу: манифест — код, элемент — процесс. После установки платформа
непрерывно сверяет декларированное состояние элемента с фактическим состоянием инфраструктуры.

### Проект, элемент, манифест

Exordos **проект** — это исходное дерево вашего приложения. Он содержит файл `exordos/exordos.yaml`, в
котором описано, как собрать один или несколько **элементов**. Каждый элемент строится из манифеста и
набора образов и артефактов:

```text
project/
├── exordos/
│   └── exordos.yaml          # конфигурация сборки: образы, артефакты, элементы
├── manifests/
│   └── my-app.yaml           # манифест для элемента "my-app"
└── src/
    └── ...                   # код приложения
```

Один проект может выпускать несколько элементов, каждый со своим манифестом. В этом руководстве мы
рассматриваем простой случай: один проект, один элемент, один манифест.

## Структура манифеста

Манифест можно разбить на несколько секций:

| Секция | Назначение |
|---|---|
| **Метаданные** | Общая информация о манифесте: имя, описание, версия и т.д. |
| **Зависимости** | Зависимости от других элементов. Например, `dbaas >= 2.1.0`. |
| **Ресурсы** | Ресурсы, необходимые для работы элемента: узлы, сервисы, конфиги, DNS-записи и т.д. |
| **Импорты** | Ресурсы, импортируемые из других элементов. Например, общая база данных. |
| **Экспорты** | Ресурсы, публикуемые данным элементом для использования другими элементами. |

### Минимальный пример

Следующий манифест определяет один элемент с одним вычислительным узлом, одним systemd-сервисом, одним
импортом (количество ядер по умолчанию из элемента `core`) и одним экспортом (сам сервис):

```yaml
name: "my_app"
description: "My web application"
schema_version: 1
version: "1.0.0"
api_version: "v1"

requirements:
  core:
    from_version: "0.0.0"

resources:
  $core.compute.nodes:
    app_node:
      name: "my-app-node"
      cores: "$my_app.imports.$default_cores:value"
      ram: 1024
      project_id: "12345678-c625-4fee-81d5-f691897b8142"
      disk_spec:
        kind: "root_disk"
        size: 10
        image: "{{ base_image_url | default('https://repo.exordos.com/exordos-base/1.1.0/exordos-base.raw.zst') }}"

  $core.em.services:
    app_service:
      project_id: "12345678-c625-4fee-81d5-f691897b8142"
      name: "my-app"
      path: "/usr/bin/python3 -m http.server 8080"
      user: "ubuntu"
      group: "ubuntu"
      target:
        kind: "node"
        node: "$core.compute.nodes.$app_node:uuid"
      service_type:
        kind: "simple"
        count: 1
      target_status: "enabled"

imports:
  default_cores:
    element: "$core"
    kind: "resource"
    link: "$core.vs.variables.$default_cores"

exports:
  my_service:
    link: "$my_app.em.services.$app_service"
```

Далее в руководстве каждая секция рассматривается подробно.

## Метаданные

Манифест начинается с полей метаданных:

```yaml
name: "core"
description: "Exordos Core element"
schema_version: 1
version: "1.0.0"
api_version: "v1"
```

| Поле | Тип | Описание |
|---|---|---|
| `name` | string | Имя элемента. Должно быть уникальным в пределах realm. |
| `description` | string | Человекочитаемое описание. |
| `schema_version` | integer | Версия схемы манифеста. Сейчас `1`. |
| `version` | string | Версия элемента, см. [exordos_devtools](https://infraguys.github.io/exordos_devtools/). |
| `api_version` | string | Версия API, на которую рассчитан манифест. Сейчас `v1`. |
| `uuid` | uuid | Необязательно. Фиксированный UUID элемента. Авто-генерируется, если опущен. |

Поля `name` и `version` вместе образуют идентичность элемента. Платформа выводит детерминированный UUID
из `{name}-{version}`, если `uuid` не указан.

## Зависимости

Секция `requirements` объявляет зависимости от других элементов. Каждая запись ключуется именем элемента
и может указывать границы версий:

```yaml
requirements:
  core:
    from_version: "1.0.0"
  dbaas:
    from_version: "2.1.0"
    to_version: "3.0.0"
```

| Поле | Тип | Описание |
|---|---|---|
| `from_version` | string | Минимальная требуемая версия (включительно). Если опущено — нет нижней границы. |
| `to_version` | string | Максимальная допустимая версия (исключительно). Если опущено — нет верхней границы. |

Ограничения версий проверяются при установке. Если требуемый элемент ещё не установлен, но
соответствующая версия доступна в зарегистрированном репозитории, он устанавливается автоматически
вместе с замыканием зависимостей. Установка завершается ошибкой, только если ни один кандидат не
удовлетворяет ограничению или установленная версия конфликтует с ним.

Зависимость `from_version: "0.0.0"` без `to_version` означает "любая версия этого элемента".

## Ресурсы

### Что такое ресурс?

**Ресурс** — это абстракция над любой инфраструктурной или платформенной сущностью, которая нужна
элементу: виртуальная машина, кластер базы данных, конфигурационный файл, DNS-запись, балансировщик
нагрузки, секрет, IAM-пользователь — всё это ресурсы с разными типами.

Секция `resources` — основная часть манифеста. Каждый ресурс имеет **тип** (ключ верхнего уровня под
`resources`) и **имя** (ключ внутри типа):

```yaml
resources:
  $core.vs.profiles:
    develop:
      name: "develop"
      profile_type: "GLOBAL"
      project_id: "12345678-c625-4fee-81d5-f691897b8142"
      description: "The develop profile"
```

Здесь `$core.vs.profiles` — тип ресурса, а `develop` — имя ресурса (ключ). Ресурсы с одинаковыми именами,
но разными типами допустимы.

### Тип ресурса

Тип — это путь через точку с префиксом `$`. Он определяет, какой элемент предоставляет данный тип
ресурса и какая коллекция API используется для его создания. Например, `$core.compute.nodes` означает,
что элемент `core` предоставляет тип `compute.nodes`, и платформа создаст ресурс через API-эндпоинт
`/v1/compute/nodes/`.

Префикс `$` сигнализирует, что тип будет вычислен при дальнейшей обработке манифеста — это не литеральная
строка, а ссылка на пространство имён предоставляющего элемента.

### Поля ресурса

Поля конкретного ресурса определяются его типом. В примере выше ресурс профиля имеет поля `name`,
`profile_type`, `project_id` и `description`. Из этих полей формируется объект, который отправляется в
API платформы для создания ресурса.

Полный справочник всех типов ресурсов и их полей см. в [Справочнике ресурсов](resources.md).

### Вложенные ресурсы

Некоторые типы ресурсов поддерживают вложенные ресурсы, адресуемые расширением пути типа через `.$name`:

```yaml
resources:
  $core.dns.domains:
    local_domain:
      name: "local.example.com"
      project_id: "12345678-c625-4fee-81d5-f691897b8142"

  $core.dns.domains.$local_domain.records:
    core_record:
      domain: "$core.dns.domains.$local_domain:uuid"
      project_id: "12345678-c625-4fee-81d5-f691897b8142"
      type: "A"
      record:
        kind: "A"
        name: "core"
        address: "10.20.0.2"
```

Здесь `$core.dns.domains.$local_domain.records` означает "записи внутри доменного ресурса `local_domain`".
Сегмент `$local_domain` — это ссылка на родительский ресурс по его ключу.

## Импорты

Если элемент зависит от ресурсов других элементов — например, общей базы данных, переменной по умолчанию
или экспортированного узла — эти ресурсы нужно **импортировать**. Секция `imports` объявляет, какие
ресурсы откуда импортировать.

```yaml
imports:
  default_cores:
    element: "$core"
    kind: "resource"
    link: "$core.vs.variables.$default_cores"
```

| Поле | Тип | Описание |
|---|---|---|
| `element` | string | Экспортирующий элемент, ссылка по его `$name`. |
| `kind` | string | Вид импорта. Сейчас поддерживается только `"resource"`. Обязателен по валидации манифеста. |
| `link` | string | Путь к ресурсу внутри экспортирующего элемента. |

Имя импорта (ключ, например `default_cores`) локально для импортирующего элемента. После импорта ресурс
можно ссылаться в секции `resources` через синтаксис `$<имя_элемента>.imports.$<имя_импорта>:field`.

### Пример: импорт узла

Элемент `test_export_node_1` экспортирует вычислительный узел:

```yaml
# test_export_node_1.yaml
name: "test_export_node_1"
# ...
resources:
  $core.compute.nodes:
    test_node:
      name: "shared-node-name"
      # ...

exports:
  shared_node:
    link: "$core.compute.nodes.$test_node"
```

Элемент `test_import_node` импортирует этот узел и использует его поля в конфиге:

```yaml
# test_import_node.yaml
name: "test_import_node"
# ...

requirements:
  core:
    from_version: "0.0.0"
  test_export_node_1:
    from_version: "0.0.0"

resources:
  $core.compute.nodes:
    dependent_node:
      name: "dependent-node"
      # ...

  $core.config.configs:
    test_config:
      project_id: "12345678-c625-4fee-81d5-f691897b8142"
      path: /home/ubuntu/test_cfg.txt
      target:
        kind: node
        node: $core.compute.nodes.$dependent_node:uuid
      body:
        kind: text
        content: |
          f"
          description={$test_import_node.imports.$shared_node:description}
          "

imports:
  shared_node:
    element: "$test_export_node_1"
    kind: "resource"
    link: "$core.compute.nodes.$test_node"
```

### Разрешение импортов

Импорты обрабатываются **до** ресурсов при установке манифеста, поэтому импортированные значения
доступны при рендеринге полей ресурсов. Платформа:

1. Ищет экспортирующий элемент по его ссылке `$name`.
2. Разрешает ссылку экспорта внутри этого элемента.
3. Создаёт запись `Import` и прокси-ресурс в движке элементов.

Если экспортирующий элемент не установлен или указанный ресурс отсутствует в его экспортах, установка
завершается ошибкой валидации.

## Экспорты

Если ресурсы элемента должны быть доступны другим элементам, их нужно **экспортировать**. Секция
`exports` публикует ресурсы под локальными именами:

```yaml
exports:
  my_service:
    link: "$core_service_example.em.services.$example_service"
    kind: "resource"
  my_node:
    link: "$core_service_example.em.services.$example_node"
```

| Поле | Тип | Описание |
|---|---|---|
| `link` | string | Путь к экспортируемому ресурсу. **Обязательно.** |
| `kind` | string | Вид экспорта. Сейчас поддерживается только `"resource"`. Может быть опущено. |

Имя экспорта (ключ, например `my_service`) локально для экспортирующего элемента. Другие элементы
ссылаются на экспорт через секцию `imports`, используя имя экспортирующего элемента и ссылку экспорта.

### Пример: экспорты элемента core

Элемент `core` экспортирует несколько ресурсов для использования другими элементами — переменные по
умолчанию, профили и локальный DNS-домен:

```yaml
exports:
  local_domain:
    link: "$core.dns.domains.$local_domain"
  var_default_cores:
    link: "$core.vs.variables.$default_cores"
  var_default_ram:
    link: "$core.vs.variables.$default_ram"
  profile_develop:
    link: "$core.vs.profiles.$develop"
```

Другой элемент может затем импортировать `var_default_cores`, чтобы получить количество ядер по умолчанию,
как показано в [минимальном примере](#минимальный-пример) выше.

### Защита при удалении

Элемент нельзя удалить, пока другие элементы объявляют его в своих `requirements`. Платформа проверяет
`requirements` установленных элементов перед удалением элемента и его ресурсов. Отметим, что одни
только импорты не защищают провайдера от удаления — если импортирующий манифест не содержит
соответствующей записи в `requirements`, провайдер всё равно можно удалить, и у импортёра останется
висящая ссылка на ресурс.

## Шаблоны манифестов

Файл манифеста может быть шаблоном Jinja2. Во время `exordos build` шаблон рендерится с переменными
времени сборки, после чего манифест включается в артефакты элемента.

```yaml
image: "{{ base_image_url | default('https://repo.exordos.com/exordos-base/1.1.0/exordos-base.raw.zst') }}"
```

В шаблонах манифестов доступны следующие переменные:

| Переменная | Описание |
|---|---|
| `{{ version }}` | Версия собираемого элемента |
| `{{ name }}` | Имя элемента |
| `{{ images }}` | Соответствие имён образов и их URN-ссылок, собранных для этого элемента |
| `{{ manifests }}` | Список файлов манифестов |

Дополнительные переменные можно передать через `exordos build --manifest-var key=value`.

Рендеринг шаблона происходит во **время сборки**. Результат — статический YAML-файл, сохранённый в
артефактах элемента. Во время установки платформа обрабатывает уже отрендеренный манифест — разрешая
`$`-ссылки и `f"..."` интерполяции (см. [Ссылки](#ссылки)).

## Ссылки

Ссылки — это механизм обращения к одному ресурсу из другого, как внутри одного элемента, так и между
элементами. Ссылка — это строка, которую платформа разрешает во время установки/реконсилиации.

### Синтаксис ссылок

Есть две формы:

**Прямая ссылка** — строка, начинающаяся с `$`:

```yaml
node: "$my_app.compute.nodes.$app_node:uuid"
```

Формат:

```text
$<элемент>.<тип_ресурса>.$<имя_ресурса>:<параметр>
```

- `<элемент>` — имя элемента (например, `my_app`, `core`).
- `<тип_ресурса>` — путь типа через точку (например, `compute.nodes`, `em.services`).
- `<имя_ресурса>` — ключ ресурса с префиксом `$`.
- `<параметр>` — поле, которое нужно извлечь из ресурса (например, `uuid`, `value`, `description`).

Если `:<параметр>` опущен, возвращается весь объект ресурса.

**Инлайн-шаблон** — строка, начинающаяся с `f"`:

```yaml
content: |
  f"
  description={$test_import_node.imports.$shared_node:description}
  "
```

Внутри строки `f"..."` плейсхолдеры `{$link:field}` заменяются разрешённым значением. Это полезно, когда
нужно встроить значение ссылки в более крупную строку (например, тело конфигурационного файла).

### Частые параметры

| Параметр | Описание |
|---|---|
| `:uuid` | UUID ресурса. Часто используется для связывания ресурсов (например, сервиса с его целевым узлом). |
| `:value` | Значение ресурса. Используется для переменных (`$core.vs.variables`). |
| `:description` | Поле описания ресурса. |
| `:default_network:ipv4` | IPv4-адрес сетевого интерфейса узла по умолчанию. |

Любое поле из фактического состояния ресурса может быть получено как параметр, включая вложенные поля,
разделённые `:`.

### Динамическое отслеживание

Ссылки не разрешаются один раз и забываются. Платформа **непрерывно отслеживает** связанные поля и
перерендеривает зависимые ресурсы при изменении значений. Это критично для динамической инфраструктуры:

- IP-адрес узла может измениться после перезагрузки или миграции.
- Значение переменной может быть обновлено администратором.
- Пул бэкендов балансировщика может получить или потерять эндпоинты.

При изменении связанного поля платформа обновляет `target_state` каждого зависимого ресурса и
реконсилирует фактическое состояние. Например, если IP узла изменился, каждый конфигурационный файл и
бэкенд балансировщика, ссылающийся на этот IP, автоматически обновляется.

## Жизненный цикл элемента

### От манифеста к элементу

Установка манифеста создаёт **элемент** — запущенный экземпляр декларированных ресурсов:

1. **Установка** — `Manifest.install()` разбирает YAML и применяет его в порядке: requirements, импорты,
   ресурсы, затем экспорты. Каждый ресурс начинает в статусе `NEW`.
2. **Реконсилиация** — цикл реконсилиации запускается каждые несколько секунд. Для каждого ресурса
   рендерится `target_state` (разрешаются ссылки и шаблоны), создаётся или обновляется `TargetResource`,
   и агент на целевом узле применяет состояние к реальной системе.
3. **Сходимость** — агент сообщает обратно `actual_resource`. Когда фактическое состояние совпадает с
   целевым, ресурс переходит в статус `ACTIVE`.

### Жизненный цикл статусов

Ресурсы и элементы имеют общий жизненный цикл статусов:

```text
NEW → IN_PROGRESS → ACTIVE
```

На уровне ресурса нет состояния `ERROR` — ресурс, который не может сойтись, остаётся в `IN_PROGRESS`.
Некоторые типы ресурсов (сервисы, конфиги) отслеживают более детальный жизненный цикл с дополнительным
статусом `ERROR`.

### Динамическая инфраструктура

Инфраструктура не статична. Узлы могут уходить, IP-адреса меняться, новые узлы присоединяться к группе.
Платформа обрабатывает это через непрерывную реконсилиацию:

- **Ссылки отслеживают изменения** — при изменении связанного поля (например, IP узла) платформа
  перерендеривает все зависимые ресурсы и отправляет обновлённые конфигурации.
- **Группы масштабируются** — ресурс `$core.compute.sets` поддерживает целевое количество реплик. Если
  узел в группе выходит из строя, платформа поднимает замену.
- **Переменные адаптируются** — `$core.vs.variables` может обновляться администраторами. Элементы,
  импортирующие эти переменные, автоматически получают новые значения на следующем цикле реконсилиации.

Поэтому ссылки фундаментальны для модели манифеста: они позволяют платформе поддерживать декларативное
желаемое состояние, пока нижележащая инфраструктура меняется.

### Обновление и удаление

- **Обновление** — установка новой версии элемента обновляет его ресурсы, импорты и экспорты на месте.
  Удалённые ресурсы удаляются; новые создаются.
- **Удаление** — элемент можно удалить, только если никакие другие элементы не объявляют его в своих
  `requirements`.
  Платформа проверяет наличие зависимых элементов перед удалением.
