# Хранилище RawStor

## Включение экспериментальной интеграции

По умолчанию интеграция RawStor в Core выключена. Чтобы включить её при сборке
образа для разработки, выполните:

```bash
RAWSTOR_ENABLED=true exordos build -f -i ~/.ssh/id_ed25519.pub
```

Сборка задаёт значение по умолчанию в шаблоне конфигурации Core внутри образа.
При обновлении существующей установки сохраняется её конфигурация. Чтобы включить
RawStor в такой установке, добавьте в `/etc/exordos_core/exordos_core.conf`:

```ini
[features]
rawstor = true
```

Выполните от root `ec-bootstrap --config-file /etc/exordos_core/exordos_core.conf`,
чтобы синхронизировать возможности агентов, затем перезапустите `ec-user-api`
и `ec-gservice`. Bootstrap синхронизирует копии конфигурации агента на диске данных.
Сохраните изменение конфигурации Core также в
`/var/lib/exordos/data/etc/exordos_core/exordos_core.conf`, чтобы оно пережило перезагрузку.

Если флаг выключен, маршруты API хранилищ и их описания OpenAPI скрыты, builder
и scheduler хранилищ не запускаются, возможность управления MDS не регистрируется
у агента, а пулы RawStor исключаются из размещения дисков. Локальные пулы qcow2
остаются доступны. Выключение флага не удаляет хранилища и не останавливает уже
запущенные ВМ, но приостанавливает управление ими. Перед выключением интеграции
на работающем стенде освободите его от нагрузок RawStor.

Ресурсы хранилищ управляются через storage API. Прямые виды ресурсов EM для
хранилищ пока не опубликованы: этот путь должен обеспечивать те же проверки
жизненного цикла и удаления.

## Создание кластера

```bash
exordos storages clusters add --type rawstor --name storage1 --host 10.100.0.2
```

Агент Core запускает отдельный `rawstor-mds@UUID.service` с собственным постоянным
индексом SQLite и зарегистрированной топологией. Агент записывает параметры
`DB_URI`, `ADVERTISE` и `DOMAIN_PATH` в `/etc/rawstor/mds/UUID.conf`.
OST регистрируются в MDS самостоятельно и продлевают регистрацию heartbeat.
Базы данных размещаются
в `/var/lib/rawstor/mds/UUID/`. Первый MDS по умолчанию использует порт 7776.
Для следующих кластеров укажите `--port` или введите свободный порт по запросу CLI.
Адрес кластера имеет вид `mds://<core-ip>:<port>/`.

Публичный `driver_spec` кластера содержит только `kind` и `endpoint`. OST и политики
пулов — отдельные ресурсы (`storages nodes` и `storages pools`). Core собирает их
текущий снимок при передаче кластера агенту; этот снимок не хранится в публичном
`driver_spec`. Поле `ost_endpoint` относилось к прежней конфигурации с одним OST
и больше не входит в API кластера.

При создании кластера добавляются две политики, использующие одну ёмкость OST:

| Пул | Tier | Ephemeral | Число копий | Домен отказа |
| --- | --- | --- | --- | --- |
| persistent | COLD | false | 2 | server |
| ephemeral | COLD | true | 1 | server |

Для постоянного диска нужны как минимум два разных сервера. Кластер из одного
сервера может размещать только временные диски. Локальные пулы qcow2 и новые
запросы на диски по умолчанию используют WARM и ephemeral. Для постоянного диска
RawStor укажите `--tier cold --no-ephemeral`.

Том машины, размещённый в кластере, хранит UUID выбранного пула в `storage_pool`
и выбранный бэкенд в `storage_backend` (`local` или `rawstor`). Переименование
локальных пулов и появление имён в виде UUID не меняют существующее назначение.
Адрес MDS относится к кластеру, а число копий, фиксированный размер чанка и домен
отказа определяются политикой пула. Core вычисляет `storage_location`
и `storage_policy` при формировании ресурса тома для агента гипервизора. Это
параметры выполнения, а не отдельные столбцы тома. Локальные тома qcow2 сохраняют
имя своего пула libvirt.

## Подготовка и регистрация OST

Подготовьте каждый узел хранения и его локальный агент:

```bash
LOCAL_GENESIS_SDK_PATH=/path/to/gcl_sdk \
  exordos storages nodes init --type rawstor --pool-agent-name my_universal_agent
```

`init` устанавливает librawstor, OST и поддержку ZFS: утилиты, модуль DKMS
и заголовки работающего ядра. Затем команда настраивает, регистрирует и запускает
локальный универсальный агент. Она добавляет `StorageNodeAgentDriver` с отдельным
файлом состояния, сохраняя UUID существующего агента и остальные его драйверы
для того же Core. `--pool-agent-name` задаёт имя локального сервиса; значение
по умолчанию — `universal_agent`. В этой функциональной ветке переменная
`LOCAL_GENESIS_SDK_PATH` выбирает соответствующий checkout SDK для виртуального
окружения агента. После выпуска совместимой версии SDK её можно не задавать.

`init` не создаёт, не запускает и не останавливает OST. Существующий OST прежнего
формата продолжает работать до явного переноса администратором.

Зарегистрируйте каждый OST через API Core с любой машины:

```bash
exordos storages nodes add --cluster storage1 --agent AGENT_UUID --name ost1 \
  --location zfs://tank/ost1 --endpoint ost://10.100.0.10:7777 \
  --failure-domain-path dc1/row1/rack1/server1
```

`add --agent` выбирает зарегистрированный агент по имени в Core или по UUID,
который выводит `init`, и создаёт ресурс OST. Команда не читает локальные
конфигурации агентов, не устанавливает пакеты, не меняет настройки агентов,
не запускает сервисы и не ждёт готовности OST. Для OST на другой машине задайте
его доступный адрес через `--endpoint`. Имя локального сервиса из
`--pool-agent-name` может отличаться от зарегистрированного имени агента;
UUID устраняет эту неоднозначность.

Агент получает желаемый ресурс в ходе согласования состояния, записывает
`/etc/rawstor/ost/UUID.conf` и запускает шаблон `rawstor-ost@UUID.service` из пакета.
Для ZFS соответствующий dataset должен существовать заранее. Для файлового
хранилища агент создаёт каталог. OST самостоятельно регистрирует адрес и failure
domain в MDS. Агент проверяет systemd-сервис; узлы, ещё не зарегистрированные
в MDS, не участвуют в расчёте доступной для новых дисков ёмкости.

Для нативного хранилища ZFS задайте `--location zfs://POOL/DATASET`. Создайте
zpool отдельно на явно выбранных дисках, затем выделите dataset для OST:

```bash
sudo zfs create -o mountpoint=none tank/ost1
```

`init` и согласование состояния не создают пулы, не форматируют диски и не
уничтожают datasets. Агент проверяет наличие dataset и использует отдельный
systemd drop-in с `User=root` и `Group=root`, необходимый для управления zvol
и доступа к блочным устройствам. Файловые OST работают от пользователя `rawstor`
с `ReadWritePaths`, разрешающим запись в их каталог. При удалении OST его
хранилище сохраняется. Для независимого учёта ёмкости выделяйте отдельный zpool
на OST: datasets одного пула используют общее свободное место, которое нельзя
учитывать несколько раз.

По умолчанию `--location` равен `file:///var/lib/rawstor/ost/UUID`. Каждый OST
должен иметь отдельную файловую систему, иначе её свободное место будет учтено
несколько раз. Для нескольких OST на одном узле нужны отдельные файловые
системы и порты. `--bind` по умолчанию использует host и порт объявленного адреса.
RawStor разрешает DNS-имена в IPv4, в том числе для адресов прослушивания.
Если объявленный адрес не принадлежит локальной машине, явно задайте локальный
`--bind`. Для прослушивания всех интерфейсов нужен `--bind 0.0.0.0:PORT`.

Если OST добавляется на той же машине без `--endpoint`, CLI определяет её адрес
и выбирает свободный управляемый порт начиная с 7777. Для удалённой машины
обязательно укажите `--endpoint`. Объявленный адрес может отличаться от bind.
Core отклоняет совпадения управляемых bind-портов и каталогов хранения на одном
хосте. В объявленном адресе допускаются IPv4 и корректные DNS-имена; имена IDN
указываются в ASCII-форме Punycode.

Путь домена отказа задаётся от внешнего уровня к внутреннему: `dc/row/rack/server`.
Короткий путь опускает внешние уровни; пропущенные домены считаются общими.
В списке узлов отображаются назначенный
агент и статус готовности.

На гипервизорах выполните `exordos hypervisors init`, чтобы установить
Python binding и rawstor-vhost.

## Управление ресурсами

Кластеры, узлы и пулы поддерживают `add`, `delete`, `list`, `show` и `update`.
Для узлов и пулов доступен `list --cluster NAME`. При совпадающих именах
в разных кластерах используйте UUID.

```bash
exordos storages clusters list
exordos storages clusters show storage1
exordos storages nodes list --cluster storage1
exordos storages nodes update OST_UUID --failure-domain-path dc1/row1/rack2/host1
exordos storages pools list --cluster storage1
exordos storages pools update POOL_UUID --mirrors 2 --failure-domain rack
```

Число копий, домен отказа, tier и ephemeral относятся к пулу. Политику нельзя
менять, пока на пул ссылаются диски или ожидающие применения ресурсы. Размер
чанка задан внутренней константой и равен 1 GiB.

Адрес MDS после регистрации менять нельзя. Удаление кластера автоматически
удаляет его пустые узлы и пулы. Операция блокируется, пока есть управляемые
или ожидающие создания диски либо неуправляемые объекты на OST. Пул нельзя
удалить, пока на него ссылаются диски. Снятие кластера с регистрации сохраняет
его базу данных и данные.

При удалении узла агент останавливает OST и удаляет его конфигурацию и drop-in.
OST уведомляет MDS о выходе; при аварийном отключении регистрация истекает
после пропущенных heartbeat. Каталоги хранения и данные остаются на месте.
Отсутствие отчёта агента не доказывает, что OST пуст. Для удаления нужно проверить
пустоту доступного OST. Перед удалением регистрации недоступного узла
восстановите доступ к его адресу.

Кластер остаётся в `DELETING`, пока агенты не подтвердят остановку всех OST.
После этого MDS останавливается через согласование состояния. В удаляемый
кластер нельзя добавлять диски, узлы и пулы. Назначенный агент и расположение
данных неизменяемы. Команда `nodes update --bind IP:PORT --endpoint ost://HOST:PORT`
меняет адреса только у кластера без управляемых дисков.

## Общая свободная ёмкость

`clusters show` показывает `capacity_info`: суммарные значения в байтах, бюджеты
каждого OST, инвентарь объектов MDS и время замера. Доступность пулов вычисляется
из одного общего инвентаря. Значения разных пулов нельзя складывать.

При размещении учитываются число копий и различные домены отказа. Ёмкость
округляется вниз до целых чанков; для ожидающих дисков резервируется место
на всех возможных узлах назначения. Изменения через API, размещение и согласование
ёмкости используют общую транзакционную блокировку PostgreSQL. Завершённые
объекты MDS считываются перед бюджетами OST, чтобы новое выделение места не
выпало одновременно из физического учёта и учёта ожидающих дисков. Когда объект
появляется в инвентаре MDS, его ожидающий резерв снимается. Недоступные OST
не дают свободной ёмкости; замеры старше 60 секунд не допускают размещение
новых дисков. Переподписки ёмкости нет.

Для ожидающих дисков оценка консервативна, для завершённого инвентаря — задаёт
верхнюю границу размещения. Окончательное решение принимает MDS: он может
отклонить выделение, если взвешенное размещение не укладывается в ёмкость узлов.
Удаление ожидающего диска снимает резерв. Удаление созданного диска освобождает
физическое место после отражения очистки OST в следующем замере. Диски RawStor
поддерживают только увеличение размера.

## Увеличение диска

Чтобы увеличить корневой диск ВМ, укажите размер в GiB:

```bash
exordos compute nodes update -u VM_UUID --root-disk 20
```

Для диска, объявленного в элементе, увеличьте размер в `disk_spec` и обновите
элемент. Для отдельного тома используйте `PUT /v1/compute/volumes/VOLUME_UUID`
с телом `{"size": 20}`. Уменьшение размера отклоняется до изменения желаемого
состояния. Текущий пул, число копий и размер чанка сохраняются. Core проверяет
только дополнительную ёмкость на назначенном пуле с учётом других ожидающих
выделений. Окончательное выделение выполняет MDS.

После увеличения объекта агент отправляет `SIGHUP` работающему vhost. Backend
переоткрывает очереди и сообщает QEMU новый размер без перезапуска ВМ. Неудачные
уведомления повторяются при обнаружении дисков; неработающий backend узнает
новый размер при следующем запуске. На существующих гипервизорах нужны
соответствующие обновлённые librawstor, Python binding и пакет vhost.
Разделы и файловую систему внутри гостя нужно расширить отдельно.

## Версия RawStor

Deb-пакеты и Python binding по умолчанию имеют версию `0.3.7` из
[RawStor v0.3.7](https://github.com/rawstor/librawstor/releases/tag/v0.3.7).
Core скачивает пакеты релиза при подготовке образа и проверяет закреплённые
SHA256. CLI скачивает OST, vhost, librawstor и binding из того же релиза.
`RAWSTOR_VERSION` выбирает релиз, а `RAWSTOR_WHEEL_VERSION` — другую версию binding,
если она отличается. Команда `nodes init --version VERSION` переопределяет
релиз для установки OST и binding. Чтобы собрать Core, задайте
`LOCAL_GENESIS_SDK_PATH`, указывающий на соответствующий checkout `gcl_sdk`
в ветке `feat/rawstor`.

## Конфигурация драйверов

Общие поля пулов — `cluster`, `name`, `tier` и `ephemeral`. Параметры RawStor
вложены в `driver_spec`:

```json
{"kind": "rawstor", "mirrors": 2, "failure_domain": "server"}
```

Общие поля узлов хранения — идентификатор, кластер, агент и статус.
`driver_spec` содержит `kind: rawstor`, `endpoint`, `location`, `bind_address`,
`failure_domain_path`. Параметры CLI не меняются: команды формируют
вложенную конфигурацию API.

Закреплённая версия требует строгого большинства для записи в зеркало.
При двух копиях данных без witness обе копии должны быть доступны для записи.
Exordos включает MDS в топологию как witness, хранящий только метаданные,
и объявляет его через bind IP и порт MDS. Домен отказа сервера остаётся UUID
узла Core. Для чётного числа копий RawStor размещает witness, позволяющий
зеркалу из двух копий сохранить большинство при потере одного узла данных.

Формат LIST различает чанки (`1`) и объекты (`2`): обновляйте клиентов, MDS
и OST вместе. Открытие зеркала только для чтения также требует кворума.
RawStor обходит эту проверку лишь при явном сочетании `FORCE` с `READONLY`.

### Граница доверия

Слушатели RawStor не аутентифицируют клиентов. Размещайте трафик MDS, OST и vhost
в доверенной сети хранения и ограничивайте доступ правилами firewall.
Настройка хранилищ — административная операция: агент обращается к объявленным
адресам, поэтому задавать их должны только доверенные администраторы.

Каталоги управляемых файловых OST должны быть непосредственными дочерними
каталогами `/var/lib/rawstor/ost`, `/data`, `/srv/rawstor` или `/mnt/rawstor`.
Компоненты-симлинки и системные каталоги отклоняются до изменения владельца.

## Запуск Core из исходников

Для установки из исходников на Linux x86-64 установите соответствующие нативные
пакеты и включите закреплённую дополнительную зависимость Python `rawstor`:

```bash
rawstor_packages=$(mktemp -d)
bash exordos/images/download_rawstor.sh "$rawstor_packages" librawstor rawstor-mds
sudo apt-get install "$rawstor_packages/librawstor_0.3.7_amd64.deb" \
  "$rawstor_packages/rawstor-mds_0.3.7_amd64.deb"
uv sync --extra rawstor
```

При последующих синхронизациях также используйте `uv sync --extra rawstor`.
Binding закреплён на релиз GitHub, но нативные библиотеки нужно устанавливать
через пакетный менеджер ОС. Образы RawStor пока требуют amd64. Образы Core
с выключенной интеграцией также поддерживают arm64.

У каждого скачиваемого файла должен быть закреплённый digest в `SHA256SUMS`.
Переопределение версии без доверенного digest отклоняется до установки.
Установочный скрипт образа Core сам устанавливает binding.

## Аккаунты проектов и совместимость обновлений

UUID аккаунта RawStor совпадает с `project_id` в Exordos. Перед созданием первого
диска проекта в MDS гипервизор идемпотентно регистрирует аккаунт. Адреса объектов
и vhost передают аккаунт как пользовательскую часть URI, например
`mds://PROJECT_UUID@core:7776/OBJECT_UUID`. При обнаружении диска проект
восстанавливается из сохранённого адреса. Нулевой UUID проекта использовать
нельзя: RawStor резервирует его для списков без фильтрации, а не для владения.

Замеры ёмкости кластера и OST остаются общими для всех проектов. Аккаунт
автоматически не удаляется при удалении диска: удаление аккаунта RawStor
удаляет также все его объекты и версии. Эта интеграция запускает RawStor
в явном режиме insecure. UUID аккаунтов — метаданные владения; контроль
доступа остаётся на стороне Exordos.

Сборка 44297955553 требует рукопожатия протокола и форматов wire и метаданных,
учитывающих аккаунты. Обновляйте librawstor, Python binding, MDS, OST и vhost
вместе. База MDS и метаданные чанков, записанные до появления аккаунтов,
несовместимы; миграции в RawStor нет. Для этой сборки пересоздайте одноразовый
кластер разработки. Обновление пакетов само по себе не конвертирует и не
удаляет существующее хранилище.

## Режим транспорта

В этой ветке MDS, OST и vhost запускаются с явным `EXTRA_ARGS="--insecure"`.
Соединения передаются открытым текстом, а peers не аутентифицируются. TLS
и выпуск SPIFFE-сертификатов находятся в отдельных ветках поверх интеграции
хранилища.

Агенты и API явно вызывают `rawstor.initialize(insecure=True)` перед загрузкой
нативных типов `Target` и `Location`. Это соответствует режиму сервисов.
Задание любых параметров `RAWSTOR_TLS_*` в insecure-режиме отклоняется.
