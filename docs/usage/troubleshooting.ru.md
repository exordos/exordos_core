Эта страница собирает типичные проблемы при разработке и развёртывании элементов на Exordos Core, а также
способы их диагностики.

## Ресурс завис в статусе `IN_PROGRESS`

Ресурсы элемента проходят жизненный цикл `NEW → IN_PROGRESS → ACTIVE`. Если ресурс не выходит из статуса
`IN_PROGRESS`, значит платформа ещё не смогла привести реальное состояние в соответствие с заявленным.

Проверьте состояние ресурса:

```bash
exordos em resources list
exordos em resources show <uuid>
```

Если ресурс так и не покидает `IN_PROGRESS`, вычислительная нода, на которую он нацелен, возможно, вообще
не поднялась. Проверьте статус ноды и гипервизора:

```bash
exordos compute nodes list
exordos compute hypervisors list
```

Чтобы узнать, на какой гипервизор размещена нода, вызовите действие `details`:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://<api>/v1/compute/nodes/<uuid>/actions/details
```

Ответ — `{"hypervisor": "<uuid>"}` с UUID гипервизора или `{"hypervisor": null}`, если нода ещё
не запланирована.

См. [Локальное развёртывание](local_deployment.md) — требования к настройке гипервизора.

## `$core.config.configs` падает вместо рендеринга

Поля `project_id` и `body.kind` у ресурса `Config` обязательны — у них нет значения по умолчанию.
Если не указать `body.kind` (например, `text`), манифест упадёт с ошибкой
`UnknownType: Unknown kind for value: ...`, а не сгенерирует пустой или неполный файл.

```yaml
$core.config.configs:
  my_config:
    project_id: "12345678-c625-4fee-81d5-f691897b8142"
    path: /etc/my_element_init.txt
    target:
      kind: node
      node: $core.compute.nodes.$my_node:uuid
    body:
      kind: text # обязательно, значения по умолчанию нет
      content: |
        ...
```

## Значения внутри содержимого конфига не подставляются

Строковые значения в манифесте интерполируются только в двух случаях:

- Значение, начинающееся с `$`, трактуется как полная ссылка на ресурс, например
  `"$core.vs.variables.$default_cores:value"`.
- Значение, начинающееся с `f"`, трактуется как inline-шаблон, в котором внутри строки подставляются
  плейсхолдеры `{$element.type.$name:field}`.

Любая другая строка — включая многострочный блок `content:` — передаётся как есть. Если забыть префикс
`f"`, плейсхолдеры `{$...}` **не** превращаются молча в пустую строку: они остаются в результирующем
выводе как буквальный текст. Если в доставленном файле оказывается
`{$core.secret.passwords.$my_password:value}` вместо реального пароля — почти всегда причина в
отсутствующем префиксе `f"`.

```yaml
body:
  kind: text
  content: |
    f"MY_PASS={$core.secret.passwords.$my_password:value}"
```

## Элемент бесконечно ждёт секрет

У ресурса `$core.secret.secrets`, у которого не заданы ни `value`, ни `default_value`, нечего
доставлять. Он остаётся в статусе `NEW`, а каждый ресурс, который рендерит из него `:value`, сохраняет
прежнее целевое состояние и пишет в лог:

```text
Target state is not available for resource <resource> by reason: 'value'
```

Проверьте, есть ли у секрета значение вообще — API его никогда не возвращает, поэтому спросите базу:

```bash
psql exordos_core -c \
  "SELECT name, status, value IS NOT NULL AS has_value,
          default_value IS NOT NULL AS has_default
   FROM secret_secrets;"
```

Задайте значение — следующий цикл реконсиляции разблокирует элемент:

```bash
curl --request PUT --location 'http://<api>/v1/secret/secrets/<uuid>' \
--header 'Content-Type: application/json' \
--header 'Authorization: Bearer $TOKEN' \
--data-raw '{"value": "the-real-value"}'
```

О том, как манифест задаёт значение по умолчанию, см. [Секреты](../secret/secrets.md).

## Bootstrap-скрипт читает пустой файл конфига

Содержимое, доставляемое через `$core.config.configs`, записывается на целевую ноду обычной записью в
файл: сначала файл создаётся (с усечением), а затем в него дозаписывается содержимое — это не атомарная
операция. Bootstrap-скрипт, запустившийся до того, как содержимое доставлено, прочитает пустой файл.

Всегда дожидайтесь, пока файл станет **непустым**, а не просто пока он появится:

```bash
while [ ! -s /etc/my_element_init.txt ]; do
    echo "Waiting for config..."
    sleep 2
done
source /etc/my_element_init.txt
```

Если скрипт уже проверяет `-s`, а файл всё равно пустой, сравните содержимое в базе данных с тем, что на
диске:

```bash
psql exordos_core -c "SELECT body FROM config_configs WHERE path = '/etc/my_element_init.txt';"
ssh ubuntu@<node-ip> "sudo cat /etc/my_element_init.txt"
```

Если значение в базе пустое — проблема в рендеринге манифеста, см. предыдущий раздел. Если в базе
содержимое есть, а на диске файла с этим содержимым нет — нода ещё не доставила его: подождите или
перезапустите bootstrap-скрипт вручную после доставки.

## Обновление Core из неопубликованной локальной сборки

Соберите образ для bootstrap и сжатый raw-образ для автономного обновления:

```bash
exordos build --element core --output-dir output .
exordos deploy --element core --element-dir output --timeout 1800
```

По умолчанию собираются форматы `qcow2,zst`. При переопределении
`GEN_IMG_FORMAT_CORE` включайте `zst`: автономное обновление записывает raw-образ
на диск и не преобразует контейнер qcow2. Манифест Core использует
`images.exordos_core_raw_zst` — ссылку `urn:images:` из сформированного inventory.
URL загрузки выбирает механизм разрешения артефактов репозитория; переменная
шаблона `repository` эту ссылку на образ не переопределяет.

Deploy без репозитория обслуживает локальную сборку, пока ждёт `ACTIVE` у Core.
Для этого нужна прямая сетевая связность между сборочной машиной и Realm.
Для удалённого Realm используйте `--repository <configured-repository>` с
доступным ему репозиторием. Источник образа должен оставаться доступным во время
перезагрузки и загрузки образа.

Перед выдачей изменённого задания гостевому агенту Core проверяет полученный URL
образа GET-запросом с Range и тайм-аутом пять секунд. HTTP-ошибка, сетевая ошибка,
отсутствие URL или пустой ответ сохраняют прежнее задание. В диагностике
реконсиляции появляется `Core update image is unavailable`; восстановите доступ
к образу в выбранном репозитории и повторите deploy. Неизменившийся образ
повторной проверки не требует.

Проверку выполняет Core, поэтому она должна уже присутствовать в работающей
версии. Она проверяет начальную доступность, но не полную загрузку, целостность
образа, условия загрузки ОС или доступность источника после перезагрузки.

### Регрессионные проверки

`tox -e build-contract` проверяет штатные рендеринг манифеста и запись inventory
в CLI без сборки VM-образа. HTTP-проверки и выдача гостевых заданий покрыты в
`exordos_core/tests/unit/compute/test_core_image_preflight.py`.

Полная приёмка обновления дополнительно требует новой изолированной VM:

1. Сохраните версии, идентификатор диска данных и контрольную запись в данных.
2. Соберите неопубликованную development-версию. Проверьте 404 публичного URL
   образа и соответствие URN в манифесте записи `raw.zst` локального inventory.
3. Выполните deploy через `exordos`, сохраняя доступность источника. Зафиксируйте
   GET образа из этого источника, перезагрузку, восстановление API и `ACTIVE`.
4. Проверьте сохранность контрольной записи, диска данных и идентичности агента.
5. На уже исправленной работающей версии Core проверьте недоступный образ:
   диагностическое сообщение, прежнее гостевое задание, прежний boot ID и
   работающий API. Восстановите доступ и проверьте продолжение штатного deploy.
